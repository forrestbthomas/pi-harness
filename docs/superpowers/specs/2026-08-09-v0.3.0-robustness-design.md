# v0.3.0 Robustness & Polish — Design

**Date:** 2026-08-09
**Status:** Approved for spec (user-reviewed section by section)
**Target release:** v0.3.0 (polished but pragmatic; not chasing 1.0 API stability)

## 1. Scope & Priorities

**Goal:** Make `pi-harness` a robust, trustworthy daily-driver harness. All 8 gaps
below are addressed, prioritized by impact, each independently shippable.

**Priority order:**

1. **Session resume** — expose `pi-run resume` / `--continue` so users can pick up
   where they left off.
2. **Eval timeouts + skip guard** — live tests must never hang; no-key runs skip
   gracefully instead of blocking.
3. **Version consistency** — build-time version derived from git, matches the tag.
4. **Error-path polish** — consistent `pi-run: <cmd>: <reason>` errors + exit-code
   documentation.
5. **Release automation** — GitHub Actions release workflow + cross-platform build
   script (stdlib-only, no goreleaser).
6. **Provider/eval test coverage** — lock in launch/flags/error behavior with
   table-driven tests.
7. **Contribution surface** — issue/PR templates, CHANGELOG, CONTRIBUTING pointers.
8. **Subagents documented** — README, project layout, example workflow; fix the
   stale "no subagent dispatch tool" lore note.

**Non-goals for v0.3.0:** API stability guarantees / 1.0 lock, cross-provider
auto-fallback, YAML provider config, non-Go dependencies.

## 2. Session Resume (#1)

**Problem:** `pi-run` launches `pi` fresh every time. Pi supports `--continue`,
`--resume`, `--session`, `--session-dir`, `--no-session`; pi-run does not expose them.

**Design:**

- Add a `pi-run resume [flags] [prompt...]` command → maps to `pi --continue`
  (latest session in `sessionDir`).
- Support pass-through of `--session <path|id>`, `--resume`, `--fork`,
  `--session-dir`, `--no-session` in `chat`/`print` (already pass-through; document
  and test).
- `pi-run resume` resolves provider/key like `chat` (same `runLaunch` path,
  mode=`chat`, extra `--continue`).
- Provider/model flags work identically: `pi-run resume --provider deepseek
  --model deepseek/deepseek-v4-pro`.

**Files:** `internal/cli/app.go` (command + dispatch), launch handling (extend
`app.go` or a new `launch.go`), `app_test.go` (table tests).

**Tests:** table-driven — `resume` → correct pi args; `--continue`/`--session`
pass-through preserved; unknown flags pass through unconsumed.

## 3. Eval Timeouts + Skip Guard (#2)

**Problem:** `pi-run eval` (full suite) hangs indefinitely without a key; live tests
spawn `pi` which blocks.

**Design:**

- **Per-test timeout** via `pytest-timeout` plugin (`--timeout=120`), so no single
  test hangs forever.
- **Runner-level no-key guard:** `pi-run eval` checks for a provider key first; if
  absent, prints a clear notice and runs only the deterministic subset (exit 0):
  `No provider key found — run pi-run doctor to check keys. Skipping live tests.`
  The Go check is env-only and synchronous: any of the `SUPPORTED_PROVIDER_KEYS`
  env vars set (OPENROUTER/OPENAI/ANTHROPIC/GEMINI/GROQ/DEEPSEEK). Bitwarden is
  not consulted here (avoids network latency in eval); env-only is the fast,
  deterministic guard. The Python suite's own `has_api_key()` still gates each
  live test (env + Bitwarden fallback) as a second layer.
- **`--quick` stays deterministic** (unchanged).

**Files:** `eval/pytest.ini` (timeout config), `eval/requirements.txt`
(+`pytest-timeout`), `eval/conftest.py` (runner-level skip guard helper),
`internal/cli/eval.go` (pre-check key presence).

**Tests:** no-key `pi-run eval` → exit 0, prints skip notice, deterministic tests
still run; live tests individually skip.

## 4. Version Consistency (#3)

**Problem:** `Version = "0.1.0"` hardcoded in `app.go`; git tag is `v0.2.0-pre`.

**Design:**

- Derive version at build time via `-ldflags "-X main.version=..."` (standard Go).
- `cmd/pi-run/main.go` declares `var version = "dev"`; `app.go` uses it (no const).
- Bump to **v0.3.0** as the next release; `version` prints the injected value
  (default `dev` when not set via ldflags).
- Build paths (`scripts/bootstrap.sh`, `internal/cli/install.go`) pass ldflags with
  current tag/commit.

**Files:** `cmd/pi-run/main.go`, `internal/cli/app.go`, `scripts/bootstrap.sh`,
`internal/cli/install.go` (or a shared `scripts/build-release.sh`), tests.

**Tests:** `version` prints injected value; default `dev` with no ldflags.

## 5. Error-Path Polish (#4)

**Problem:** Commands return bare exit codes with terse/absent messages.

**Design:**

- Consistent error format: every failure prints `pi-run: <command>: <reason>` to
  stderr before returning the code.
- Document exit codes (0 ok, 1 generic, 2 usage, 3 missing key, 4 node/pi missing,
  5 eval venv missing) in `help` and README.
- Wrap `runEval`/`runSetup`/`runDoctor` to surface underlying errors (e.g.
  `eval failed: exit 5 (eval/.venv missing — run pi-run setup)`). Concrete
  messages: `eval failed: eval/.venv missing — run pi-run setup`,
  `setup failed: pip install exited 1`, `doctor failed: <reason>`.
- Keep exit codes stable; only messages become consistent.

**Files:** `internal/cli/app.go` (dispatch wraps errors), `eval.go`/`setup.go`/
`doctor.go` (message improvements), `app_test.go`.

**Tests:** table — each failure path prints `pi-run: <cmd>: ...` and returns the
correct code.

## 6. Release Automation (#5)

**Problem:** No automated release; `pi-run install` is manual.

**Design:**

- Add `.github/workflows/release.yml` triggered on `v*` tags: checkout, setup-go,
  build `bin/pi-run` for **linux/darwin/windows × amd64/arm64**, attach binaries as
  release artifacts, with ldflags version injected.
- Keep dependency-light: `scripts/build-release.sh` cross-compiles the matrix with
  `GOOS/GOARCH` + ldflags (no goreleaser).
- Tag **v0.3.0** when this work lands.

**Files:** `.github/workflows/release.yml`, `scripts/build-release.sh`, `README.md`
(release section).

**Tests:** `scripts/build-release.sh` produces binaries for all targets locally
(spot-check one).

## 7. Contribution Surface (#7)

**Problem:** No issue/PR templates, no CHANGELOG.

**Design:**

- Add `.github/ISSUE_TEMPLATE/bug_report.md` and `feature_request.md`.
- Add `.github/PULL_REQUEST_TEMPLATE.md` (summary, test plan, checklist).
- Add `CHANGELOG.md` (manual, curated; no tool), starting with v0.3.0.
- Reference templates + changelog convention in `CONTRIBUTING.md`.

**Files:** `.github/ISSUE_TEMPLATE/*.md`, `.github/PULL_REQUEST_TEMPLATE.md`,
`CHANGELOG.md`, `CONTRIBUTING.md` (update).

**Tests:** templates render; CONTRIBUTING references them.

## 8. Subagents Documented (#8)

**Problem:** `pi-subagents` is enabled (commit 3c15b13) but undocumented; stale lore
note says the harness has no subagent tool.

**Design:**

- README: add "Subagent-Driven Development" section (what's installed, how to
  invoke, the 6 builtin agents: scout/researcher/worker/reviewer/oracle/delegate).
- Project layout: mention `.pi/` packages include `pi-subagents`.
- Example (`examples/subagents.md`): scout → worker → reviewer using the harness's
  own files.
- AGENTS.md: update the stale "no subagent dispatch tool" lore note.

**Files:** `README.md`, `examples/subagents.md`, `AGENTS.md` (lore note update),
possibly `.lore.md`.

**Tests:** docs render; example workflow is plausible.

## Testing Strategy (cross-cutting)

- Go: `go test ./...`, `go vet ./...`, `go build ./...` (CI + local).
- Python: `pi-run eval --quick` (deterministic subset) + `config-check`.
- Release: `scripts/build-release.sh` spot-check.
- No secrets in tests; no hardcoded user paths in shipped code (existing scan).

## Rollout

Each item is independently shippable; land in priority order. Tag `v0.3.0` after all
8 land, with the release workflow producing artifacts.
