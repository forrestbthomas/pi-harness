# Go Toolchain Bump to 1.26 — Design

**Date:** 2026-08-10
**Status:** Proposed (user requested research + spec)
**Target release:** v0.4.2 (patch — toolchain-only, no user-visible behavior change)

## 1. Context & Motivation

`pi-run` (the harness CLI) is built with **Go 1.21.5** — pinned in `go.mod`,
all three GitHub Actions workflows (`ci.yml`, `release.yml`, `nightly-live-eval.yml`),
and the README. That is now two full release lines out of date:

- **Go 1.21 is past end-of-life.** Go's support policy covers each major release
  until two newer majors exist; 1.21 stopped receiving security fixes after
  Go 1.24 shipped (2025-02-11). We are shipping a CLI that processes API keys
  and spawns subprocesses on a **no-longer-patched toolchain**.
- **Latest stable is Go 1.26.5** (released 2026-07-07). 1.26 is the current
  major line (1.26.0 shipped 2026-02-10; patch series includes security fixes
  to `crypto/x509`, `crypto/tls`, `net/url`, `os`, `html/template`, and the
  `go` command).
- The 1.21 → 1.26 jump includes 5 major releases (1.22–1.26) of runtime,
  compiler, and stdlib improvements: faster GC (Green Tea GC default in 1.26),
  generic type aliases (1.24), range-over-int / iterators (1.23), `os/exec`
  hardening, and many security fixes. For a **stdlib-only** CLI the upgrade is
  low-risk and mostly a toolchain/CI/docs change.

**Versioning:** user confirmed this lands as the next **patch** release (v0.4.2)
— it is a maintenance/toolchain change with no user-visible CLI behavior change.

### 2.2 Feasibility probe (done on this machine)

Set `go.mod` to `go 1.26.5` locally (with `GOTOOLCHAIN=auto` auto-downloading
Go 1.26.5) and ran the full suite:

```
go build ./...   → exit 0
go vet ./...     → exit 0
go test ./...    → ok (all packages pass)
```

**Zero code changes required.** The codebase uses only stable stdlib APIs
(`os/exec`, `context`, `filepath`, `os`, `encoding/json`, `testing`, `bytes`)
that are unchanged or backward-compatible in 1.26. `go mod tidy` under 1.26
keeps the directive as `go 1.26.5` and adds **no** `toolchain` line (no external
deps).

### 2.3 Relevant Go 1.26 changes (why this is low-risk for us)

- **Language:** `new` accepts an initializer expression; self-referential generic
  type constraints allowed. Both additive; we use neither.
- **Stdlib changes that touch our imports:** `os/exec` (hardened further; no
  breaking API change for `CommandContext`), `os` (additive `Process.WithHandle`),
  `filepath` (no breaking change), `bytes.Buffer.Peek` (additive), `testing`
  (additive helpers), `encoding/json` (no breaking change). `net/url.Parse` now
  rejects malformed colon-in-host URLs (`http://::1/`) — we don't parse such
  URLs in Go (Pi handles provider URLs).
- **Runtime:** Green Tea GC default (performance), heap base randomization
  (security). No behavioral risk for a short-lived CLI.
- **`go.mod` semantics:** `go` directive = minimum required version; a toolchain
  below it refuses to load the module. `GOTOOLCHAIN=auto` (default) auto-fetches
  the required toolchain, so developers on older Go get a clean, guided switch.
- **Bootstrap:** Go 1.26 requires Go 1.24.6+ to bootstrap — irrelevant for CI
  (`setup-go` installs the requested toolchain directly).
- **`actions/setup-go@v7`** supports Go 1.26 (version syntax incl. `1.26.5`).

### 2.4 One nuance for the README badge

The badge currently hardcodes `Go-1.21`. Options: bump to `Go-1.26` or use the
dynamic `https://img.shields.io/badge/Go-1.26-blue` (same style). Keep the
hardcoded badge but update the value — no new badge service needed.

## 3. Scope

### In scope (the bump + adopting modern language/tooling)

**A. Toolchain bump (baseline, always in)**

1. `go.mod`: `go 1.21.5` → `go 1.26.5` (then `go mod tidy`; expect only the
   directive line to change).
2. CI workflow `go-version` values: `'1.21'` → `'1.26.5'` in all three files
   (ci, release, nightly).
3. README: badge `Go-1.21` → `Go-1.26`; "Go 1.21+" → "Go 1.26+ (only to build
   /update `pi-run`)".
4. CHANGELOG: v0.4.2 entry (see §5).
5. Verify: full `go build/vet/test ./...`, `pi-run eval --quick`, and the
   cross-language contract test still pass under 1.26.5 in CI.

**B. Adopt 1.22–1.26 language/stdlib features where they simplify real code**

Concrete opportunities found by scanning the current code (each is
behavior-preserving; adoption is opportunistic, not forced):

1. **`for i := range n` (Go 1.22)** — `pi.go:138` `semverGreater` uses
   `for i := 0; i < 3; i++`; rewrite as `for i := range 3`.
2. **`errors.As` / `errors.AsType` (1.26)** — three sites type-assert
   `err.(*exec.ExitError)` directly (`pi.go:87`, `setup.go:72`,
   `secret_contract_test.go:122`). Switch to `errors.AsType[*exec.ExitError]`
   so wrapped errors are found too (more robust, same behavior for
   non-wrapped cases).
3. **`slices` package (1.21+ stdlib)** — `config_check.go:142` hand-rolls
   `firstIndexOf`; replace with `slices.Index` (and drop the helper).
   `toStrings` stays (generic conversion of `[]any`).
4. **`maps`/`slices` elsewhere** — only where a hand-rolled loop is strictly
   worse; no forced rewrites of already-clear loops.
5. **`t.Context()` (1.24)** — in tests that build a context (e.g. timeout
   tests), prefer `t.Context()` over `context.Background()` for automatic
   cancellation on test end.
6. **`go vet` under 1.26** — the newer toolchain's analyzers run on the whole
   tree; fix anything new it flags (expect none, per probe).
7. **Race detector in CI** — add `go test -race ./...` to the CI `go` job.
   The codebase is small and stdlib-only; race is cheap here and locks in
   concurrency safety (the secret-timeout tests exercise goroutines/timeouts).

**C. "Latest and greatest tools" (build/tooling hygiene)**

1. **`go fix` modernizers (1.26)** — the revamped `go fix` applies idiomatic
   modernizations automatically. Run `go fix ./...` after the bump and review
   the diff (expect small/no-op for this codebase; accept only clearly
   behavior-preserving fixes).
2. **`go mod tidy` / `go mod verify`** — confirm no drift, no `toolchain` line
   added (stdlib-only).
3. **`pi-run version` smoke in CI** — already covered by the release workflow;
   keep.

**Explicitly NOT adopting** (overkill for this stdlib-only CLI, or would add
churn without benefit):

- `iter`/range-over-func (1.23) — no custom iterators needed; the 27 existing
  `for ... range` loops are already idiomatic.
- Generic type aliases (1.24) — no alias-heavy API surface.
- `new(T)(expr)` initializer (1.26) — no allocation sites that benefit.
- `bytes.Buffer.Peek`, `io.ReadAll` changes, `errors.AsType` in production
  hot paths — nothing to gain.
- `math/rand/v2` (1.22) — the CLI does not use `math/rand` at all.
- New crypto packages (1.26) — CLI does not do cryptography.
- Staticcheck / golangci-lint — external tools would break the zero-external-
  deps philosophy; `go vet` + `go fix` cover the stdlib-only surface.
- **Upgrading the local `/usr/local/go` install** — not required:
  `GOTOOLCHAIN=auto` fetches 1.26.5 on demand. (Optional user-machine
  follow-up, not a repo change.)
- Python dependency bumps — unrelated; deps were just bumped in v0.4.1.
- Any user-visible CLI behavior change — binaries stay functionally
  identical; only toolchain + internal code style change.

## 4. Implementation Plan (ordered, each independently shippable)

1. **`go.mod` bump** — set `go 1.26.5`, run `go mod tidy` + `go mod verify`,
   confirm diff is just the directive line.
2. **CI workflows** — update `go-version` to `1.26.5` in `ci.yml`, `release.yml`,
   `nightly-live-eval.yml` (3 lines); add `go test -race ./...` to the CI `go`
   job. CI proves the toolchain bump; release binaries are built with 1.26.5;
   nightly eval unaffected.
3. **Feature adoption sweep** (behavior-preserving, each reviewed):
   - `semverGreater`: `for i := 0; i < 3; i++` → `for i := range 3`.
   - `err.(*exec.ExitError)` at `pi.go:87`, `setup.go:72`,
     `secret_contract_test.go:122` → `errors.AsType[*exec.ExitError]`.
   - `firstIndexOf` helper → `slices.Index`; drop helper.
   - `t.Context()` in tests where a context is constructed.
   - Run `go fix ./...`; review and accept only clearly behavior-preserving
     modernizations.
   - Re-run full suite; confirm no behavior change.
4. **README** — badge + "Go 1.26+" prerequisite line (2 spots).
5. **CHANGELOG** — cut v0.4.2 section.
6. **Verification gates** (must all pass before merge):
   - `go build ./...`, `go vet ./...`, `go test ./...`, `go test -race ./...`
     under 1.26.5 (CI does this).
   - `pi-run eval --quick` (deterministic smoke subset) passes.
   - Cross-language secret-backend contract test (`TestSecretBackendContractMatchesPython`)
     passes (it runs `python3 eval/secret_backend.py`, unaffected by toolchain).
   - No hardcoded-user-path test regressions (`TestNoHardcodedUserPaths`).
7. **Merge via PR** (main is branch-protected) → tag `v0.4.2` → release workflow
   builds binaries with 1.26.5 → Homebrew tap auto-updates (formula unchanged,
   only shas change).

## 6. Risks & Mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| New stdlib behavior change breaks a test | Low (probe passed) | CI `go` job runs full suite under 1.26.5 before merge |
| `setup-go` + `1.26.5` resolves differently than local | Low | `setup-go@v7` documents 1.26 support; same version string as local probe |
| Developers on old Go get a confusing error | Low | `GOTOOLCHAIN=auto` (default) auto-downloads the required toolchain with a clear message |
| Release binaries differ subtly (GC, heap randomization) | Very low | Functionally identical CLI; covered by `pi-run version` smoke in the formula test |
| Some contributor has Go < 1.24.6 and no network for auto-fetch | Low | Guided `GOTOOLCHAIN` message; CI is authoritative |
| Feature adoption changes behavior (errors.AsType on wrapped errors, `go fix`)
  | Low | Every adoption is behavior-preserving and reviewed; full suite incl. `-race` gates the PR |
| Race detector slows CI | Low | Codebase is small and stdlib-only; negligible added wall time |

## 7. Decision

**Recommendation: proceed with the bump to Go 1.26.5 + feature adoption as
v0.4.2.** The bump is low-risk (probe passed with zero code changes) and
removes a security liability (unsupported toolchain). The feature-adoption
sweep (Section 3B) is deliberately conservative — only `for i := range n`,
`errors.AsType`, `slices.Index`, `t.Context()`, `go fix` modernizers, and the
race detector — each grounded in a real site in the current code, each
behavior-preserving. Features that would add churn without benefit (`iter`,
generic aliases, new crypto, `math/rand/v2`) are explicitly excluded.

The alternative — bumping only to a supported-but-older line like 1.24 — buys
little: 1.24 is already one major behind and would need another bump within
months. Go **1.25.12** (the last 1.25 patch, 2026-07-07) is also fully
supported, but the codebase is stdlib-only and 1.26.5's probe is clean, so
there is no practical reason to stop short.
